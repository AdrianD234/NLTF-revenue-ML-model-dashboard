# Known assurance issue — arbitration values disagree with the page

**Not caused by this branch. Not fixed in this PR.** Recorded so it is a
tracked finding rather than an unexplained red test.

## Symptom

`tests/test_playwright_dashboard.py::test_latest_arbitration_values_are_visible_not_stale`
fails:

```
assert '3.13%' in 'Current Parquet finalists using Paper-style horizon MAPE:
  Heavy RUC: 2.29% qtr / 1.68% annual; Light RUC: 5.36% qtr / 1.27% annual;
  PED: 3.22% qtr / 2.17% annual. Lower is better.'
```

The test reads `artifacts/chart_sources/overview_finalist_forecast_accuracy.csv`
and requires each `metric_display` to appear in the page's chart-info text.
The CSV says PED **3.13% / 1.95%**; the page renders PED **3.22% / 2.17%**.

## Why it is not this branch

1. **The file is untracked.** `git ls-files artifacts/chart_sources/` returns
   only three files, and this is not one of them. It is regenerated by
   `write_chart_source_tables` on every app load, so no branch can change it
   in version control.
2. **Nothing in this branch touches the path.** The diff contains no change to
   `chart_sources.py`, `r2_metrics.py`, `r2_ladder.py`, `evidence_pack.py` or
   `data/dashboard_evidence_pack/**`. The value is a model-accuracy metric
   from the scorecard predictions, entirely separate from the Revenue Outlook
   long-run work.
3. **The page showed 3.22% before any of this work.** The first read of the
   running dashboard in this session — on merged `main`, before a single edit
   — reported "PED VKT per capita … 3.22% quarterly MAPE | 2.17% annual".

## What it actually is

Two code paths inside the app disagree about the same metric: the CSV writer
(`_overview_finalist_accuracy`) and the on-page chart-info text. One of them
is computing over a different filter or a different score basis. Since the
CSV is a regenerated artifact rather than a stored input, "staleness" is the
wrong description — it is an internal inconsistency, and the test named
"…_are_visible_not_stale" is detecting it correctly.

## Why it has gone unnoticed

`pytest.ini` sets `addopts = -m "not e2e"`, and the clean-clone CI job runs
with e2e deselected (45 deselected). The browser suite therefore never runs
in CI, so this assertion has never been enforced there.

## Routing

Belongs with the repository-assurance sweep (audit generators and checks that
can't see the failure they exist to catch). Two questions for it:

1. Which of the two paths is right — is the displayed 3.22% or the written
   3.13% the governed number?
2. Should the browser suite run in CI at all? A test family that cannot fail
   the build is only as good as the person who remembers to run it.
